🎨 System Design Core: Real-Time Collaborative Canvas

  • Delta-State Sync: Only strokes and mutation events are sent over WebSockets (~80 bytes) rather than the entire 500KB canvas bitmap, saving 98%+ bandwidth.
  • Monotonic Sequence IDs: Every delta is stamped with an incrementing seq number so clients can detect dropped packets or packet reordering.
  • Compaction & Snapshots: Every 50 operations, the server compacts history into a snapshot to ensure newly joining users hydrate in 1 round-trip.
  • Ephemeral Presence: Live cursor positions are broadcast to peers without hitting disk storage.

💡 System Design Tip: Multi-User Concurrency

In production apps like Google Docs or Figma, conflicts are handled using either Operational Transformation (OT) or Conflict-free Replicated Data Types (CRDTs). In this canvas, we use deterministic sequential ordering (Last-Write-Wins with immutable delta elements) for high-framerate multi-user drawing.

🚩 System Design Core: Feature Flag Engine

  • Sub-Millisecond In-Memory Reads: Never make a network call on if (flags.isEnabled()). The client SDK caches configs locally and evaluates them in <0.05ms.
  • Server-Sent Events (SSE) Streaming: When an admin toggles a flag, the change is streamed to all connected clients over SSE instantly.
  • Consistent Hashing Rollouts: hash(userId + flagKey) % 100 < rolloutPercent ensures the exact same user always gets the exact same feature variation without storing user state.

⏰ System Design Core: Delayed Queues & Idempotency

  • Idempotency Keys: If a client network request times out, retrying with the same idempotencyKey returns the existing job without creating duplicate social posts.
  • Delayed Priority Queue: Jobs are stored with future timestamps (scheduledAt). A background worker tick pulls and locks due jobs.
  • Exponential Backoff Retries: Transient downstream API errors trigger automatic retries (2s, 4s, 8s).
  • Dead-Letter Queue (DLQ): Poison pills that fail 3 times are moved to DLQ for manual inspection, preventing head-of-line blocking.

🛡️ System Design Core: API Rate Limiter Gateway

  • Token Bucket: Tokens refill smoothly at rate $R$ up to capacity $C$. Allows short burst traffic up to bucket capacity, then meters at steady refill rate.
  • Sliding Window Counter: Tracks request timestamps over rolling window $W$, preventing edge-burst 2x rate spikes across fixed window boundaries.
  • Standard RFC Headers: Returns X-RateLimit-Limit, X-RateLimit-Remaining, and Retry-After: 429.

📰 System Design Core: Activity Feed & Fan-Out Architectures

  • Fan-Out on Write (Push): Write event directly to all followers' inboxes. Read is instantaneous $O(1)$, but writing to a celebrity with 10M followers causes write amplification.
  • Fan-Out on Read (Pull): Store events only on author's stream. Followers pull and merge-sort on demand. Write is $O(1)$, but reading is heavy $O(K \log K)$.
  • Hybrid Mode: Standard users use Fan-Out on Write; celebrities (>5 followers in this lab) use Fan-Out on Read.
  • Cursor Pagination: Avoids database OFFSET performance degradation by paginating via timestamp/ID cursors.

📦 System Design Core: Distributed Chunked Object Storage (S3-Lite)

  • Metadata vs Chunk Separation: Metadata (filename, size, MIME type, chunk manifest) is stored separately from raw binary chunks.
  • Content-Addressable Storage (CAS): Chunks are keyed by their SHA-256 hashes, enabling automatic deduplication across files.
  • Replication Factor 2: Every chunk is placed on 2 distinct storage nodes.
  • Fault Tolerance & Failover: Simulate a crash on Storage Node A. Reading a file automatically fails over to replica Node B or Node C without data loss!

🎯 FAANG Interview Questions Mapped to Each Module INTERVIEW DRILLS
1. "Design Figma or Google Docs" (Whiteboard)

Interviewer Trap: "Should we store canvas state in SQL?"
Winning Answer: Never store rapid stroke deltas directly in SQL. Use WebSockets terminating on a stateful gateway cluster. Transmit immutable mutation deltas using CRDTs or deterministic operational transforms, and flush compacted snapshots to S3 periodically.

2. "Design LaunchDarkly" (Feature Flags)

Interviewer Trap: "How do you handle 1 million RPS checking flags?"
Winning Answer: Zero network requests on flag evaluations. The SDK downloads rules once and evaluates in-memory using consistent hashing (hash(userId + key) % 100). Invalidation is pushed via SSE / streaming gRPC.

3. "Design Stripe Webhook Dispatcher / Buffer" (Scheduler)

Interviewer Trap: "What happens if a worker crashes midway or the merchant endpoint times out?"
Winning Answer: Enforce idempotency keys on every job. Workers lock jobs via atomic CAS/Redlock with TTL. Transient failures trigger exponential backoff retries (2s, 4s, 8s). Poison pills move to DLQ to avoid head-of-line blocking.

4. "Design Cloudflare / API Gateway Rate Limiter"

Interviewer Trap: "Fixed window vs Sliding window vs Token bucket?"
Winning Answer: Fixed window is vulnerable to 2x boundary traffic spikes. Token bucket is ideal for allowing short bursts up to bucket capacity while strictly metering sustained rate. Implement via atomic Redis Lua scripts to prevent read-modify-write race conditions.

5. "Design Twitter / Instagram Activity Feed"

Interviewer Trap: "Do you push or pull?"
Winning Answer: Hybrid model! Push (fan-out on write) for 99.9% of users for blazing $O(1)$ read performance. Pull (fan-out on read) for celebrities (e.g. Elon Musk with 180M followers) to avoid freezing message queues with 180 million database writes on every post.

6. "Design Amazon S3 / Google Cloud Storage"

Interviewer Trap: "Where do you store metadata vs files?"
Winning Answer: Strictly decouple metadata (Spanner/Postgres) from chunk storage (blob disks). Break files into fixed content-addressable SHA-256 chunks. Use consistent hashing rings for chunk placement and Reed-Solomon erasure coding (e.g. 8+4) for storage efficiency over raw 3x replication.
